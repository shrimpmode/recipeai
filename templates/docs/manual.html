Nutrition Goal RAG

How this project turns a sentence like “something high in fibre for lunch” into three recipes that also suit the user's nutrition goals. Covers the architecture, the database schema, the pgvector search layer and how to run it.

Django 5.1 Postgres 16 + pgvector 0.8 Celery + Redis all-MiniLM-L6-v2 · 384d Claude Haiku 4.5

01Overview

The app is a small retrieval-augmented generation (RAG) system over a catalogue of recipes with nutrition data. A logged-in user types a request in plain language. The app then works in three stages:

  1. Retrieve. It embeds the request with a local sentence-transformers model and pulls the 15 nearest recipes from Postgres using pgvector.
  2. Re-rank. If the user has set daily nutrition goals, it narrows those 15 down to the 5 whose per-serving nutrition best fits one meal's share of the day.
  3. Generate. It asks Claude to pick the best 3 of the shortlist and write a one- or two-sentence reason for each.

Claude can only choose from recipes the database returned. Any recipe ID outside the shortlist is discarded, so the model cannot invent a recipe.

02Architecture

Runtime topology

There are two processes, web and worker, and both run the same image and the same Django project. Neither keeps state of its own: everything persistent lives in Postgres, and Redis only carries the task queue. The web process never calls the embedding model or Claude. It records the request, puts a task on the queue and returns, so a slow LLM call cannot hold up a web worker.

Solid boxes are services we run. Dashed boxes are third parties: the Hugging Face Hub is used only by the batch commands, and the Claude API only by the worker. Teal edges are the worker's calls while it resolves one query.

Request lifecycle

  1. Submit. POST / creates a QueryRequest (status pending), calls resolve_query.delay(id) and returns a small HTMX fragment that polls for the result.
    queries/views.py · submit_query
  2. Pick up. The worker marks the request running and logs query_resolution_started with its query_request_id, which then appears on every log line for this request.
    queries/tasks.py · resolve_query
  3. Embed the prompt. The worker turns the prompt into a 384-dimension vector, in-process, with no network call.
    recipes/services/embeddings.py · embed_query
  4. Retrieve. It fetches the 15 recipes nearest to the prompt by cosine distance, skipping recipes that have no embedding yet. The HNSW index serves this query.
    queries/services/retrieval.py · retrieve_by_similarity
  5. Re-rank (only if the user has goals). Each daily target is divided by 3 to get one meal's share. Each candidate gets the mean relative deviation from those targets, and the 5 closest are kept. Without goals, the top 5 by similarity are kept.
    queries/services/retrieval.py · rerank_by_goals
  6. Generate. The worker sends the shortlist to Claude as JSON and gets back [{recipe_id, description}]. Any ID that was not in the shortlist is dropped and logged (selection_outside_candidates).
    queries/services/generation.py · select_and_describe
  7. Persist or retry. On success, the worker writes exactly 3 results to QueryRequest.results and sets status done. On failure, it retries up to QUERY_TASK_MAX_RETRIES times, waiting 2 s, then 4 s, then 8 s, before setting status error.
    queries/tasks.py
  8. Poll. GET /queries/<id>/status/ returns the results, the error message, or another polling fragment. It is scoped to the owner, so asking for another user's request returns 404.
    queries/views.py · query_status

Known gap: every error is retried. The retry loop treats every exception as transient, so a revoked API key (401) still waits through all its backoff delays before failing. The planned fix is to fail permanent errors (400, 401, 403) on the first attempt and keep retrying timeouts, 429s and 5xx responses.

Keyword search (no AI)

The search page has an AI search / Keyword search switch. Keyword search is GET /search/?q=…. It runs one query synchronously, with no Celery task, embedding or Claude call, and returns at most KEYWORD_SEARCH_RESULT_COUNT (5) recipes, along with the time the search took.

  • Matching: every word must appear, ignoring case, in the recipe name or an ingredient line. Recipes whose name contains every word come first, then alphabetical. Only the first 8 words are used.
  • Indexes: pg_trgm GIN indexes on the same expressions the ORM generates (recipes.models.ingredients_as_text is shared by the index and the query). A test asserts the planner can use both indexes, because a mismatch would fall back to a full scan without any error.
  • Still a full scan: words under 3 characters (they have no trigrams) and very common words such as salt, which is in about 60% of recipes. For those, Postgres is right to scan.

04Vector database

Why pgvector, not a separate vector store

The vectors live in a vector(384) column on recipes_recipe. At this scale, a separate vector database would bring more complexity than benefit:

One transaction

A recipe's text and its vector change together, so there is no second store to keep in sync and nothing to drift.

Filters are just SQL

embedding IS NOT NULL today; dietary or meal-type filters could later be ordinary WHERE clauses next to the kNN ordering.

One thing to operate

Backups, migrations, monitoring and access control all reuse the Postgres setup we already run.

When to revisit: tens of millions of vectors, or an index that no longer fits in RAM. See scaling notes.

What gets embedded

Each recipe is turned into one document by dataset.compose_embedding_text. It joins the name, the ingredients, the labels, the meal and dish types, and a summary of the nutrition per serving, separated by ". ". Putting the nutrition in the text lets a prompt like “high protein” match on meaning, before any numeric re-ranking.

Why HNSW rather than IVFFlat: HNSW can be built on an empty or growing table and needs no training step. It also gives better recall for the same speed. IVFFlat's lists have to be rebuilt as the data changes, which does not suit a corpus that keeps getting reloaded.

Query path

The ORM call in retrieve_by_similarity compiles to:

SELECT *
  FROM recipes_recipe
 WHERE embedding IS NOT NULL
 ORDER BY embedding <=> $1::vector(384)
 LIMIT 15;

Check that the index is used with EXPLAIN. Look for an Index Scan using recipe_embedding_hnsw line:

docker compose exec db psql -U nutrition -c "EXPLAIN ANALYZE SELECT id FROM recipes_recipe
  WHERE embedding IS NOT NULL ORDER BY embedding <=> (SELECT embedding FROM recipes_recipe LIMIT 1) LIMIT 15;"

Filtered search with HNSW. HNSW applies a WHERE clause after it walks the graph, so a selective filter can leave you with fewer than LIMIT rows. Our current filter, IS NOT NULL, is free because NULL vectors are never in the index. If you add selective filters such as health_labels ? 'Vegan', turn on pgvector 0.8's SET hnsw.iterative_scan = relaxed_order, or raise hnsw.ef_search.

Embedding lifecycle

The database itself acts as the work queue. A recipe needs embedding when either of these is true:

embedding IS NULL                    -- new row, or a reload changed its text
OR embedding_model <> 'all-MiniLM-L6-v2'  -- embedded by a different model
  • Resumable. The backfill reads the stale rows in id order with keyset pagination, 512 per batch. It embeds each batch outside any transaction, then commits it with bulk_update. If the run is interrupted, at most one batch is lost, and re-running carries on from where it stopped.
  • Changing the model is the same command. Point LocalEmbedder.model_id at the new model (and change EMBEDDING_DIMENSIONS and add a migration if the dimension changes), then run backfill_embeddings. Rows that have not been re-embedded yet still answer queries until the run finishes.
  • A query never mixes models. Today there is one model, so this holds automatically. During a model change, rows from both models sit in the same column. If both models had the same dimension, a query could compare the new query vector against vectors from the old model. If the two models ever share a dimension, also filter retrieval on embedding_model.

05Ingestion pipeline

The corpus is datahiveai/recipes-with-nutrition (licence CC BY-NC 4.0). Loading it is a two-stage batch job: load_corpus handles the relational data and takes seconds, then backfill_embeddings handles the vectors and takes about a minute. The full reasoning is in docs/adr/0001-corpus-load-pipeline.md.

  1. Fetch. hf_hub_download downloads default/train/0000.parquet at a pinned commit of refs/convert/parquet, about 100 MB compared with 450 MB for the CSV. The file is cached locally, so later runs do not download it again. Change PARQUET_REVISION deliberately: Hugging Face can regenerate that branch.
  2. Lock and record. pg_try_advisory_lock lets only one load run at a time; a second one fails at once with LoadInProgress. Then an IngestionRun row is created with the file's sha256.
  3. Validate and stage. pyarrow reads the file in record batches. Each row is parsed and validated in Python. Valid rows are streamed into the unlogged staging table with COPY, and invalid ones are written to ingestion_reject.
  4. Reconcile. If source_rows ≠ staged + rejected, the run is marked as failed before anything reaches the live table.
  5. Merge. A single set-based statement does the upsert: DISTINCT ON (recipe_name) drops duplicate names, ON CONFLICT updates the data columns, and an existing vector is kept only if its input hash is unchanged.
  6. Backfill. Embeds every stale row, as described in §4.

06Operations

Full corpus load (runbook)

docker compose exec db pg_dump -U nutrition -Fc nutrition > backup.dump   # before the first load
docker compose run --rm worker python manage.py migrate recipes 0003      # schema only, no vector index yet
docker compose run --rm worker python manage.py load_corpus               # fetch → stage (COPY) → merge; seconds
docker compose run --rm worker python manage.py backfill_embeddings       # slow; Ctrl-C safe, re-run to resume
docker compose run --rm worker python manage.py migrate                   # HNSW index on embeddings

Health queries

-- Recent loads
SELECT id, status, source_rows, staged_rows, rejected_rows, inserted_rows, updated_rows,
       finished_at - started_at AS took
  FROM recipes_ingestionrun ORDER BY id DESC LIMIT 5;

-- Why rows were rejected, by reason
SELECT reason, count(*) FROM ingestion_reject WHERE run_id = :run GROUP BY 1 ORDER BY 2 DESC;

-- Embedding coverage
SELECT embedding_model, count(*) FILTER (WHERE embedding IS NULL) AS pending, count(*)
  FROM recipes_recipe GROUP BY 1;

-- Recipes no longer in the latest source
SELECT count(*) FROM recipes_recipe
 WHERE last_seen_run_id IS DISTINCT FROM (SELECT max(id) FROM recipes_ingestionrun WHERE status = 'succeeded');

Real database in tests

Tests run against the real pgvector container: the merge SQL, COPY, the advisory lock and the HNSW index are all tested against Postgres itself.

Fakes only at the edges

The embedding model is swapped for a FakeEmbedder passed in through the Embedder protocol; the Claude call is patched at generation.select_and_describe.

Fixtures are real Parquet

Each test writes a small Parquet file with the same column types as the real source, so pyarrow follows the same code path as in production.
